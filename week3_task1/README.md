# Week 3 · Task 1 — Infrastructure provisioning with Terraform

## Задача

Описать Terraform инфраструктуру для приложения [nodejs-demoapp](https://github.com/benc-uk/nodejs-demoapp)
и поднять её в двух окружениях: группа автомасштабирования EC2, где приложение
запускается в Docker через user data, за балансировщиком нагрузки.

## Что развёрнуто

```
интернет ──80──> Application Load Balancer ──80──> Auto Scaling Group (EC2 + Docker)
                                                          │
                                                          └──27017──> DocumentDB (Task 3)
```

| Компонент | Как сделано |
|---|---|
| Сеть | VPC, 2 публичные подсети в разных AZ (для ALB), 2 приватные (для базы), интернет-шлюз. NAT-шлюза нет намеренно |
| Security groups | три слоя, каждый принимает трафик только от предыдущего по ссылке на security group, а не по CIDR |
| Балансировщик | `terraform-aws-modules/alb` 10.5.1, target group на 80, health check на `/` |
| Группа | `terraform-aws-modules/autoscaling` 9.3.1, launch template с user data, health check type `ELB` |
| Масштабирование | target tracking по `ASGAverageCPUUtilization`, цель 40% |
| Роль инстансов | `AmazonSSMManagedInstanceCore` — заход без SSH, инвентарь, сканирование Inspector |
| Оповещения | SNS + уведомления группы + алармы CloudWatch (бонусная часть) |

## Структура

```
week3_task1/
├── README.md
├── artillery/load-test.yml        нагрузочный сценарий
├── user_data/user_data.sh         установка Docker и запуск контейнера
└── infrastructure/
    ├── common/                    единственное место с описанием ресурсов
    ├── env/                       dev.tfvars, production.tfvars
    ├── dev/                       main.tf + симлинки на common
    └── production/                main.tf + симлинки на common
```

`main.tf` в окружении — **настоящий файл**, а не симлинк: в нём блок `backend`
со своим ключом состояния, а два файла с одинаковым именем в одном каталоге
существовать не могут. Остальные шесть файлов подключены символическими
ссылками, поэтому описание ресурсов существует в одном экземпляре.

## Как запустить

```bash
cd infrastructure/dev
terraform init
terraform plan -var-file=../env/dev.tfvars -out=dev.tfplan
terraform apply dev.tfplan
terraform output alb_dns_name
```

Для второго окружения — то же самое из `infrastructure/production`
с `-var-file=../env/production.tfvars`.

Перед первым запуском нужно заменить имя бакета для состояния
в `dev/main.tf` и `production/main.tf`.

## Окружения

| | dev | production |
|---|---|---|
| Тип инстанса | `t3.micro` (1 ГиБ) | `t3.small` (2 ГиБ) |
| Инстансов | 1, потолок 2 | 2 в разных AZ, потолок 4 |
| Узлов DocumentDB | 1 | 2 в разных AZ |
| Сеть | `10.30.0.0/16` | `10.40.0.0/16` |

`dev` — место, где проверяют, что код применяется. `production` — где живёт
отказоустойчивость: два инстанса в разных зонах доступности и реплика базы,
которая становится primary автоматически. Одинаковый размер сделал бы
разделение окружений чисто символическим.

## Нагрузочное тестирование

Инструмент — **Artillery 2.0.34**, сценарий в [artillery/load-test.yml](artillery/load-test.yml).
Четыре фазы на 15 минут: разогрев 60 с по 1 запросу в секунду, нарастание 180 с до 10,
удержание 600 с на 10, спад 60 с. Каждый виртуальный пользователь проходит `/` → `/info` → `/tools/load`.

Форма нагрузки важнее её величины. Первый прогон давал пики до 47% и провалы до 7%,
и политика масштабирования на него не реагировала: target tracking просыпается только
после **трёх минут подряд** выше цели. Понадобилось ровное плато, а не рекорд.

## Наблюдение за масштабированием

Полный цикл эластичности, обе стороны:

```
08:51   CPU перешёл порог 40%
08:54   AlarmHigh → политика cpu-target: desired 2 → 3, запуск i-07dea5e2b4acaa64d
08:56   CPU упал до 36% — нагрузка размазалась на три инстанса
09:16   AlarmLow  → политика cpu-target: desired 3 → 2
09:22   завершение i-07dea5e2b4acaa64d
```

Оба аларма создаёт сама политика target tracking, мы их не описывали:

| | Масштабирование вверх | Масштабирование вниз |
|---|---|---|
| Аларм | `AlarmHigh` | `AlarmLow` |
| Порог | 40% (наша цель) | **28%** — AWS вывел сам, 70% от цели |
| Периодов по 60 с | **3** | **15** |
| Задержка реакции | ~3 минуты | ~15 минут |

**Асимметрия пятикратная, и она осмысленна.** Цена двух ошибок разная: не добавить мощность
вовремя — отказ в обслуживании, не убрать вовремя — несколько центов. Зазор между 40% и 28%
защищает от «дребезга», когда группа добавляет и убирает инстанс по кругу.
