# Week 3 · Tasks 1 and 3 — Terraform infrastructure and its security

## Task 1 — задача

Описать Terraform инфраструктуру для приложения [nodejs-demoapp](https://github.com/benc-uk/nodejs-demoapp)
и поднять её в двух окружениях: группа автомасштабирования EC2, где приложение
запускается в Docker через user data, за балансировщиком нагрузки.

## Что развёрнуто

```
интернет ──80──> Application Load Balancer ──80──> Auto Scaling Group (EC2 + Docker)
                                                          │
                                                          └──27017──> DocumentDB (Task 3)
```

| Компонент | Как сделано |
|---|---|
| Сеть | VPC, 2 публичные подсети в разных AZ (для ALB), 2 приватные (для базы), интернет-шлюз. NAT-шлюза нет намеренно |
| Security groups | три слоя, каждый принимает трафик только от предыдущего по ссылке на security group, а не по CIDR |
| Балансировщик | `terraform-aws-modules/alb` 10.5.1, target group на 80, health check на `/` |
| Группа | `terraform-aws-modules/autoscaling` 9.3.1, launch template с user data, health check type `ELB` |
| Масштабирование | target tracking по `ASGAverageCPUUtilization`, цель 40% |
| Роль инстансов | `AmazonSSMManagedInstanceCore` — заход без SSH, инвентарь, сканирование Inspector |
| Оповещения | SNS + уведомления группы + алармы CloudWatch (бонусная часть) |

## Структура

```
week3_task1/
├── README.md
├── artillery/load-test.yml        нагрузочный сценарий
├── user_data/user_data.sh         установка Docker и запуск контейнера
└── infrastructure/
    ├── common/                    единственное место с описанием ресурсов
    ├── env/                       dev.tfvars, production.tfvars
    ├── dev/                       main.tf + симлинки на common
    └── production/                main.tf + симлинки на common
```

`main.tf` в окружении — **настоящий файл**, а не симлинк: в нём блок `backend`
со своим ключом состояния, а два файла с одинаковым именем в одном каталоге
существовать не могут. Остальные шесть файлов подключены символическими
ссылками, поэтому описание ресурсов существует в одном экземпляре.

## Как запустить

```bash
cd infrastructure/dev
terraform init
terraform plan -var-file=../env/dev.tfvars -out=dev.tfplan
terraform apply dev.tfplan
terraform output alb_dns_name
```

Для второго окружения — то же самое из `infrastructure/production`
с `-var-file=../env/production.tfvars`.

Перед первым запуском нужно заменить имя бакета для состояния
в `dev/main.tf` и `production/main.tf`.

## Окружения

| | dev | production |
|---|---|---|
| Тип инстанса | `t3.micro` (1 ГиБ) | `t3.small` (2 ГиБ) |
| Инстансов | 1, потолок 2 | 2 в разных AZ, потолок 4 |
| Узлов DocumentDB | 1 | 2 в разных AZ |
| Сеть | `10.30.0.0/16` | `10.40.0.0/16` |

`dev` — место, где проверяют, что код применяется. `production` — где живёт
отказоустойчивость: два инстанса в разных зонах доступности и реплика базы,
которая становится primary автоматически. Одинаковый размер сделал бы
разделение окружений чисто символическим.

## Нагрузочное тестирование

Инструмент — **Artillery 2.0.34**, сценарий в [artillery/load-test.yml](artillery/load-test.yml).
Четыре фазы на 15 минут: разогрев 60 с по 1 запросу в секунду, нарастание 180 с до 10,
удержание 600 с на 10, спад 60 с. Каждый виртуальный пользователь проходит `/` → `/info` → `/tools/load`.

## Наблюдение за масштабированием

Полный цикл эластичности, обе стороны:

```
08:51   CPU перешёл порог 40%
08:54   AlarmHigh → политика cpu-target: desired 2 → 3, запуск i-07dea5e2b4acaa64d
08:56   CPU упал до 36% — нагрузка размазалась на три инстанса
09:16   AlarmLow  → политика cpu-target: desired 3 → 2
09:22   завершение i-07dea5e2b4acaa64d
```

Оба аларма создаёт сама политика target tracking, мы их не описывали:

| | Масштабирование вверх | Масштабирование вниз |
|---|---|---|
| Аларм | `AlarmHigh` | `AlarmLow` |
| Порог | 40% (наша цель) | **28%** — AWS вывел сам, 70% от цели |
| Периодов по 60 с | **3** | **15** |
| Задержка реакции | ~3 минуты | ~15 минут |

**Асимметрия пятикратная, и она осмысленна.** Цена двух ошибок разная: не добавить мощность
вовремя — отказ в обслуживании, не убрать вовремя — несколько центов. Зазор между 40% и 28%
защищает от «дребезга», когда группа добавляет и убирает инстанс по кругу.

# Task 3 — Infrastructure Security and DocumentDB

Инфраструктура та же, что в Task 1: код лежит в `infrastructure/common/`, ресурсы
DocumentDB и Inspector управляются флагами `enable_docdb` и `enable_inspector`
в `env/*.tfvars`. Отдельного каталога у задачи нет намеренно — база и её защита
не существуют в отрыве от приложения, которое они обслуживают.

## Препятствие, которого не было в задании

Первая попытка поднять кластер завершилась отказом на уровне аккаунта:

```
FreeTierRestrictionError: The specified cluster engine type is not available
with free plan accounts. Available engine types: [aurora-postgresql]
```

Аккаунт был в режиме **AWS Free Plan**, а он блокирует не отдельные классы
инстансов, а сервис целиком. Тот же режим до этого не дал запустить `t3.medium`
в группе автомасштабирования — там ошибка была
`The specified instance type is not eligible for Free Tier`.

Вариантов было три: перейти на Paid Plan, подменить DocumentDB на разрешённую
Aurora PostgreSQL или ограничиться `terraform plan` и объяснением в отчёте.
Выбран первый: задание требует именно DocumentDB, а подмена движка сломала бы
раздел `/todo` — приложение умеет только MongoDB. Кредиты при переходе
сохраняются, поэтому решение ничего не стоило.

## 1. DocumentDB для приложения

**Кода писать не пришлось.** Приложение уже умеет MongoDB: в `src/todo/routes.mjs`
есть раздел «список задач», который включается сам при наличии переменной
окружения `TODO_MONGO_CONNSTR`, а DocumentDB совместим с MongoDB по протоколу.

Что создаётся (`infrastructure/common/docdb.tf`):

| Ресурс | Значение | Почему так |
|---|---|---|
| `aws_docdb_subnet_group` | две приватные подсети | требование сервиса — минимум две AZ |
| `aws_docdb_cluster` | engine `docdb 5.0.0` | |
| `manage_master_user_password` | `true` | пароль генерирует и хранит AWS, в состояние Terraform он не попадает |
| `storage_encrypted` | `true` | шифрование на диске, стоит ноль |
| `aws_docdb_cluster_instance` | `db.t4g.medium` ×1 | самый дешёвый поддерживаемый класс, $0.08924/час |

**Про пароль отдельно.** Документация провайдера предупреждает прямым текстом:
все аргументы, включая `master_password`, сохраняются в состоянии **открытым
текстом**. Вариант с паролем в переменной означал бы пароль в `terraform.tfstate`,
а часто и в `tfvars` рядом с кодом. С `manage_master_user_password` наружу
отдаётся только ARN секрета, а инстанс читает его сам по своей IAM-роли.

Подключение собирается в `user_data/user_data.sh` при старте инстанса:

```
mongodb://<user>:<pass>@<endpoint>:27017/?tls=true
  &tlsCAFile=/certs/global-bundle.pem&replicaSet=rs0
  &readPreference=secondaryPreferred&retryWrites=false
```

Три параметра здесь обязательны и неочевидны: TLS в DocumentDB включён всегда
и требует бандла сертификатов Amazon RDS, который монтируется в контейнер
с хоста; `retryWrites=false` нужен потому, что DocumentDB не поддерживает
повторяемые записи, а драйвер MongoDB включает их по умолчанию.

**Проверка** — не по странице в браузере, а по логу приложения:

```
### 🚀 Node.js demo app v4.9.9 starting...
### 🌐 Server listening on port 3000
### ✅ Enabled Todo app. Connected to MongoDB!
```

## 2. Security groups — три слоя, ни одного CIDR внутри

| Группа | Входящее | Источник |
|---|---|---|
| `week3-dev-alb-sg` | 80/tcp | `0.0.0.0/0` — интернет |
| `week3-dev-app-sg` | 80/tcp | **security group балансировщика** |
| `week3-dev-docdb-sg` | 27017/tcp | **security group приложения** |

Правила ссылаются на другую группу, а не на диапазон адресов. Это даёт две вещи.
Во-первых, инстансы недостижимы напрямую даже с публичным IP: подключение
к их адресу минует балансировщик и не попадает под правило. Во-вторых, правило
не нужно править при масштабировании — новая машина попадает под него
автоматически, просто потому что состоит в нужной группе.

Исходящий трафик приложения тоже сужен, вместо разрешённого по умолчанию
«всё куда угодно»: 443 (реестр образов, Secrets Manager, SSM), 80 (репозитории
пакетов `dnf`) и 27017 к базе.

Правила заданы отдельными ресурсами `aws_vpc_security_group_ingress_rule`,
а не inline-блоками. Смешивать эти два способа нельзя: inline-блоки считают
себя единственным источником истины и при следующем `apply` удаляют правила,
добавленные отдельными ресурсами.

## 3. IAM — принцип наименьших привилегий в буквальном виде

К роли инстанса `week3-dev-app` прицеплены ровно две политики:

| Политика | Зачем |
|---|---|
| `AmazonSSMManagedInstanceCore` | заход на инстанс без SSH, сбор инвентаря, сканирование Inspector |
| `week3-dev-read-docdb-secret` | чтение одного секрета с паролем базы |

```json
{
  "Effect": "Allow",
  "Action": ["secretsmanager:GetSecretValue"],
  "Resource": ["arn:aws:secretsmanager:eu-central-1:<account-id>:secret:rds!cluster-07cefb87-..."]
}
```

`Resource` — конкретный ARN одного секрета, а не `"*"`. Утечка роли даёт
злоумышленнику пароль от одной базы, а не все секреты аккаунта.

**Чего IAM здесь НЕ делает.** У DocumentDB нет аутентификации через IAM —
в отличие от RDS с `rds-db:connect` или DynamoDB. Действия `docdb:Connect`
не существует, и никакая политика не пустит и не остановит запрос к порту 27017:
это работа security group. IAM контролирует доступ к **паролю**, а не к базе.

Итого доступ закрыт тремя независимыми слоями: сеть (приватные подсети без
маршрута наружу), security group (только от группы приложения), учётные данные
(секрет, читаемый только ролью инстанса).

## 4. AWS Inspector

Включается ресурсом `aws_inspector2_enabler` с `resource_types = ["EC2"]`.
Это переключатель уровня аккаунта, а не объект: сканирование распространяется
на все инстансы, включая поднятые не этим Terraform.

Чтобы сканирование заработало, инстанс должен быть виден в Systems Manager —
Inspector забирает через него инвентарь пакетов. Роль с
`AmazonSSMManagedInstanceCore` заведена ещё в Task 1, поэтому покрытие
составило **100% (1 из 1 виртуальной машины)** без дополнительных настроек.

Результат: **одна находка, severity Low**.

```
Port 80 is reachable from ...   | Network Reachability | i-0f4762f46c0cca717
```

**Это истинная находка, и правильный ответ на неё — «да, так и задумано».**
Путь «интернет → ALB → инстанс:80» существует специально, приложение для этого
и развёрнуто. Важно, что именно смягчает риск: инстанс принимает трафик
**только от security group балансировщика**, а не от произвольного хоста.

Ноль критических находок — не потому, что всё идеально, а потому что образ
свежий и ОС только что установлена. Ценность Inspector не в одном прогоне,
а в том, что он пересканирует ресурсы при появлении новых CVE.

**Вывод, важный для неизменяемой инфраструктуры:** Inspector здесь не инструмент
патчинга, а **триггер пересборки**. Патчить работающий инстанс бессмысленно —
группа автомасштабирования заменит его на новый из старого шаблона. Исправление
находки означает обновить AMI и прокатить instance refresh.

## Инцидент: пароль со спецсимволом

После того как кластер поднялся, приложение продолжало отвечать, health check
оставался зелёным, страница `/todo` рендерилась — но `/api/todo` возвращал
**500 Internal Server Error**.

Причина обнаружилась только в логе контейнера:

```
### 💥 ERROR! MongoParseError: Password contains unescaped characters
```

Сгенерированный AWS пароль содержал `#`. В URI этот символ начинает якорь,
поэтому драйвер MongoDB обрезал строку подключения и отверг её. Логин и пароль
теперь процентно кодируются перед подстановкой:

```python
urllib.parse.quote(json.load(sys.stdin)["password"], safe="")
```

`safe=""` обязателен: без него `quote()` оставляет `/` нетронутым, а он ломает
строку так же надёжно.

Два вывода стоят того, чтобы их записать:

**Ошибка не проявляется там, где её ищут.** Метрики были зелёными, инфраструктура
по всем признакам исправна, а функция не работала. Метрики показывают, что
система жива, но не что она делает правильно.

**Сгенерированный пароль — не обычная строка.** Любая подстановка секрета в URL,
строку подключения или командную строку требует кодирования. Это общее правило,
а не частный случай MongoDB.

## Что осталось незакрытым

| Пробел | Почему так | Что сделали бы в production |
|---|---|---|
| ALB работает по HTTP без сертификата | нет домена, ACM требует валидации | домен + сертификат ACM, listener 443, редирект с 80 |
| Инстансы в публичных подсетях | NAT-шлюз стоит $0.052/час — дороже всей остальной инфраструктуры | приватные подсети + NAT либо VPC-эндпоинты |
| Один узел базы в `dev` | второй удваивает самую дорогую позицию | в `production` заложено два узла в разных AZ |
| `deletion_protection = false` у кластера | иначе `destroy` не проходит и забытый кластер стоит $2.1 в сутки | `true` плюс финальный снапшот |
| Роль `week3-terraform` с `AdministratorAccess` | точный список действий заранее не собрать | сузить по факту через IAM → Generate policy based on CloudTrail events |
| Нет WAF, VPC Flow Logs, GuardDuty | не требовалось заданием и платно | включены, логи в отдельный аккаунт |
| Сканируется только EC2 | образ берётся из чужого реестра | свой образ в ECR + сканирование образов тем же Inspector |

Отдельно про последний пункт. Приложение запускается из
`ghcr.io/benc-uk/nodejs-demoapp:latest` — чужого образа с плавающим тегом.
Форк при этом не является источником того, что работает: правка кода
в репозитории на инстансы не влияет, а автор образа может опубликовать новую
версию в любой момент, и следующее масштабирование поднимет уже её. Правильный
путь — собирать свой образ из форка, публиковать в ECR с тегом по SHA коммита
и тянуть оттуда. Тогда же закрывается и сканирование образов, и вопрос
с сертификатом для DocumentDB: бандл кладётся в образ вместо монтирования
с хоста.
