# Week 3 · Task 2 — Infrastructure provisioning with Terragrunt

Та же инфраструктура, что в Task 1, собранная заново: не одним состоянием на
окружение через симлинки, а семью независимыми юнитами с автоматическим
графом зависимостей.

## Структура

```
terragrunt/
├── root.hcl                  backend, provider, хук оценки стоимости
├── _envcommon/               тело каждого юнита, общее для всех окружений
│   ├── vpc.hcl  sg.hcl  alb.hcl  ec2.hcl
│   ├── docdb.hcl  autoscaling.hcl  cloudwatch.hcl
├── modules/                  пять собственных модулей, у каждого README
│   ├── security/             три security group одной цепочкой
│   ├── docdb/                кластер DocumentDB + IAM-политика на секрет
│   ├── launch_template/      AMI, IAM-роль, user data, шаблон запуска
│   ├── app_asg/              группа и политика масштабирования
│   └── cloudwatch/           SNS, уведомления группы, алармы
├── dev/         env.hcl + vpc/ + app/{sg,alb,ec2,docdb,autoscaling,cloudwatch}/
├── production/  та же структура, свой env.hcl
└── loadtest/    та же структура, свой env.hcl
```

Состав юнитов повторяет схему из задания. Сверх неё добавлен `app/docdb`

## Как это устроено

**Юнит — это одно состояние.** Каталог с `terragrunt.hcl` соответствует одному
вызову модуля и одному файлу состояния в S3. Ключ вычисляется из пути:

```hcl
key = "terragrunt/${path_relative_to_include()}/terraform.tfstate"
```

Одна строка в `root.hcl` — и `dev/vpc`, `dev/app/alb`, `production/vpc`
оказываются в разных файлах без единой настройки в самих юнитах. В Task 1 то же
самое делалось руками: два файла `main.tf`, скопированных целиком ради одной
различающейся строки.

**Юнит занимает 12 строк**, из которых 9 — два блока `include`:

```hcl
include "root" {
  path = find_in_parent_folders("root.hcl")
}

include "envcommon" {
  path           = "../../../_envcommon/alb.hcl"
  merge_strategy = "deep"
}
```

Всё содержательное живёт в `_envcommon/` и вычисляется из `env.hcl`. Без этого
слоя `dev/app/alb/terragrunt.hcl` и `production/app/alb/terragrunt.hcl` были бы
двумя почти одинаковыми файлами по 60 строк — ровно то дублирование, против
которого задание и предостерегает.

**Порядок применения считает Terragrunt.** Граф строится по блокам `dependency`:

```
vpc → sg ─┬→ alb ────────┐
          ├→ docdb → ec2 ┴→ autoscaling → cloudwatch
```

Проверяется командой `terragrunt dag graph`. В Task 1 этот порядок держался
в голове.

## Почему `root.hcl`, а не `terragrunt.hcl`

Схема в задании показывает корневой `terragrunt.hcl` — это практика, от которой
Gruntwork отказались. Terragrunt не мог отличить корневую конфигурацию от юнита
и пытался применить корень как инфраструктуру. С версии 1.x рекомендуется
`root.hcl`, а `find_in_parent_folders()` вызывается с явным именем файла.

Это единственное намеренное отклонение от схемы.

## Сравнение с Task 1

| | Симлинки (Task 1) | Terragrunt (Task 2) |
|---|---|---|
| Состояние | одно на окружение | одно на юнит, семь на окружение |
| `plan` | вся инфраструктура разом | только изменённый юнит |
| Радиус ошибки | сломанный ресурс блокирует всё | ломается один юнит |
| Параллельная работа | один человек = окружение заблокировано | разные юниты независимы |
| Настройка backend | копия в каждом окружении вручную | вычисляется из пути |
| Порядок создания | держишь в голове | считает Terragrunt |
| Новое окружение | каталог + расстановка симлинков + свой `main.tf` | каталог + `env.hcl` |
| Работает на Windows | нет без `core.symlinks=true` | да |

**Цена третьего окружения — 33 строки.** Весь `loadtest/` это 117 строк, из
которых 84 — семь юнитов по 12 строк (те самые два `include`), и только
`env.hcl` на 33 строки содержит что-то своё: сеть `10.50.0.0/16`, потолок
группы 8 вместо 4. Ни один файл в `_envcommon/` и ни один модуль не изменились.

Окружение не только описано, но и проверено: `terragrunt run --all plan`
прошёл по всем семи юнитам. В плане ресурсы названы `week3-loadtest-...` —
значит параметры из `env.hcl` дошли до модулей, а не потерялись по дороге.

Отличий от `production` ровно три: имя окружения, диапазон сети и потолок
группы. Тип инстанса, размер группы и число узлов базы совпадают намеренно —
нагрузочный стенд, отличающийся от production, даёт числа, которые никуда
не переносятся. Более высокий потолок нужен, чтобы тест мог перешагнуть
рабочий предел и показать, где система ломается.

## Пять модулей

Задание требует один собственный модуль. Получилось пять — не ради количества,
а потому что границы напрашивались сами.

| Модуль | Почему это отдельная сущность |
|---|---|
| `security` | три группы, связанные ссылками друг на друга, имеют смысл только вместе |
| `docdb` | кластер, узлы, subnet group и политика на секрет — одна сущность из четырёх ресурсов |
| `launch_template` | «какая машина»: образ, роль, user data |
| `app_asg` | «сколько машин и где»: границы группы и политика масштабирования |
| `cloudwatch` | наблюдение меняется чаще инфраструктуры |

Разделение `launch_template` и `app_asg` продиктовано схемой задания, но
оказалось осмысленным: шаблон правят при смене образа или user data, группу —
при изменении потолка нагрузки. Разные поводы, разная частота.

У каждого модуля свой README с таблицами входов и выходов.

## Оценка стоимости

Infracost встроен хуком в `root.hcl` и срабатывает на команде `plan` в любом
юните любого окружения — как требует задание: «running a plan produces a cost
estimate alongside the Terraform plan».

```
── оценка стоимости: dev/app/alb
  Name                     Monthly Qty  Unit  Monthly Cost
  aws_lb.this                       ...
```

| Окружение | Оценка в месяц | Основной вклад |
|---|---|---|
| `dev` | **$85.06** | DocumentDB $65, балансировщик $20 |
| `production` | **$150.20** | два узла базы, два инстанса |
| `loadtest` | **$150.20** | повторяет production намеренно |

Совпадение `production` и `loadtest` — подтверждение замысла, а не ошибка:
нагрузочный стенд должен повторять production, иначе результаты теста никуда
не переносятся. Отличается только потолок группы, а он на постоянную стоимость
не влияет.

**Что эти цифры значат.** Infracost считает стоимость ресурсов по прайс-листу,
а не будущий счёт: трафик, число запросов и объём хранилища ему неизвестны, для
них есть отдельный `infracost-usage.yml` с предположениями. Правильная
формулировка — «оценка постоянной части стоимости».

Отключить оценку при отладке: `TG_SKIP_INFRACOST=1 terragrunt plan`.

### Общие входы в `root.hcl` ломают чужие модули

В корневой конфигурации лежал блок:

```hcl
inputs = {
  name_prefix = local.name_prefix
  ...
}
```

Terragrunt передаёт входы из `root.hcl` **каждому** юниту. У модуля
`terraform-aws-modules/alb` есть своя переменная `name_prefix`, взаимоисключающая
с `name`. Юнит `alb` получил обе и упал на `plan`:

```
"name": conflicts with name_prefix
```

Соблазн положить что-нибудь «общее» в корень велик, но работает это только пока
все модули свои. Блок убран: каждый юнит передаёт ровно то, что нужно его модулю.

### Функции Terragrunt ломают Infracost

Пути к локальным модулям были написаны через `get_repo_root()`. Infracost
вычисляет корень репозитория по-своему — пути превращались в
`terragrunt/terragrunt/modules`, и оценка выходила пустой.

Все `source` и `include` переведены на относительные пути:
`../../../modules//security`. Конфигурация стала проще и перестала зависеть от
того, как внешний инструмент понимает «корень репозитория».

Исключение — `user_data_path`: это значение для `templatefile()`, который
резолвит относительные пути от рабочего каталога Terraform, то есть от
`.terragrunt-cache`. Там оставлен `get_terragrunt_dir()`.

### Infracost 2.x несовместим с `_envcommon`

В новой мажорной версии появилась проверка путей:

```
Security problem: include path .../_envcommon/alb.hcl is not within an allowed directory
```

Под неё попадает ровно тот паттерн, который Gruntwork рекомендует для устранения
дублирования. Результат: 2.x разбирает часть юнитов и выдаёт неполную оценку,
0.10.x — все семь. Флага, ослабляющего проверку, в 2.x нет.

Два рекомендованных инструмента, чьи соглашения столкнулись. Выбрана работающая
комбинация — Infracost 0.10.45, — а не свежая версия ради свежести. Хук
определяет доступную подкоманду сам (`breakdown` в 0.10.x, `scan` в 2.x),
поэтому конфигурация переживёт обновление, когда несовместимость починят.
