# Модуль `cloudwatch`

Оповещения о событиях масштабирования: тема SNS, подписка по почте, уведомления группы
и алармы. Отдельный юнит `app/cloudwatch` по структуре задания.

## Почему отдельно

Наблюдение меняется чаще инфраструктуры: пороги подкручивают, адреса добавляют. Держать
это в одном состоянии с сетью и группой означает трогать всё ради правки одного числа.

## Что создаёт

| Ресурс | Роль |
|---|---|
| `aws_sns_topic` | точка доставки, одна на все оповещения окружения |
| `aws_sns_topic_subscription` | подписка по почте, только если задан адрес |
| `aws_autoscaling_notification` | события группы: запуск, завершение и оба `*_ERROR` |
| `aws_cloudwatch_metric_alarm.high_cpu` | средняя загрузка CPU выше порога |
| `aws_cloudwatch_metric_alarm.high_latency` | время ответа целей выше порога |

## Входы

| Имя | Тип | По умолчанию | Описание |
|---|---|---|---|
| `name` | `string` | — | базовое имя |
| `autoscaling_group_name` | `string` | — | группа, за событиями которой следим |
| `alb_arn_suffix` | `string` | `""` | пустая строка — аларм по времени ответа не создаётся |
| `alert_email` | `string` | `""` | пустая строка — тема есть, подписки нет |
| `cpu_alarm_threshold` | `number` | `70` | процентов |
| `latency_alarm_threshold` | `number` | `3` | секунд |
| `tags` | `map(string)` | `{}` | дополнительные теги |

## Выходы

`sns_topic_arn`, `subscription_arn`, `alarm_names`.

## Сигнал управления против сигнала тревоги

Порог аларма по CPU — **70%**, а цель политики масштабирования — **40%**. Это не
рассогласование, а разные назначения:

| Аларм | Порог | Кто создал | Роль |
|---|---|---|---|
| `TargetTracking-...-AlarmHigh` | 40% / 3 мин | политика масштабирования | **управляет** ёмкостью |
| `<name>-asg-high-cpu` | 70% / 2 мин | этот модуль | **предупреждает** человека |
| `<name>-alb-high-latency` | 3 с / 2 мин | этот модуль | **предупреждает** человека |

Пока система справляется сама, будить человека незачем. На нагрузочном тесте первым
сработал аларм по времени ответа: процессор был загружен на 43%, а запросы ждали
по 4 секунды — задержка автомасштабированием не лечится.

## Две ловушки подписки по почте

**Подтверждение — действие человека, Terraform его не контролирует.** `apply` завершится
успешно, а письма приходить не будут, пока не нажата ссылка Confirm subscription. Умолчание
провайдера на ожидание — одна минута, здесь поднято до десяти.

**Подписку можно убить из почтового клиента** — ссылкой unsubscribe в подвале письма или
кнопкой «Отписаться», которую Gmail рисует сам по заголовку `List-Unsubscribe`. Такое
удаление идёт мимо IAM, не видно в CloudTrail, и Terraform его не замечает: SNS помечает
подписку `Deleted`, но не убирает, поэтому `plan` показывает «no changes». Лечится только
явным `terragrunt apply -- -replace=aws_sns_topic_subscription.email[0]`.
